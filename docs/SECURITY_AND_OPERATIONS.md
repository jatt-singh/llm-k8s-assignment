# Security and operational decisions

## Security controls

| Layer | Control | Where |
|---|---|---|
| **Supply chain** | Every base image pinned by digest (`golang`, `distroless/static`, `llama.cpp`, `curl`, `kindest/node`). Helm charts and Terraform providers pinned to exact versions (+ `.terraform.lock.hcl`) | Dockerfiles, `values.yaml`, `variables.tf`, `versions.tf` |
| | Model pinned to a Hugging Face **commit**, with SHA-256 verified before use and re-verified daily | [MODEL.md](MODEL.md) |
| | Trivy image scan gate (fixable ≥ CRITICAL fails, configurable), full reports kept, SPDX SBOM per image | `scripts/ci.sh scan/sbom`, `reports/` |
| | Trivy misconfiguration scan of the rendered chart (HIGH/CRITICAL fails) and of Terraform (report) | `scripts/ci.sh lint` |
| | Minimal images: Go services are static binaries on distroless (no shell, no package manager, ~21 MB) | `services/Dockerfile` |
| **Container** | `runAsNonRoot`, uid/gid 65532, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem: true`, `seccompProfile: RuntimeDefault`, explicit `emptyDir` for `/tmp` where needed | `_helpers.tpl` (shared by all pods) |
| | Upstream llama.cpp image runs as root, so it is wrapped with `USER 65532` | `llm/Dockerfile` |
| **Namespace** | Pod Security Standards: `llm-app` **enforce=restricted**; `monitoring` baseline (warn/audit restricted); `ingress` privileged (hostPort on Kind only) | `app.tf`, `modules/platform` |
| **Identity / RBAC** | One ServiceAccount per workload, `automountServiceAccountToken: false`, **no Roles bound**. No app workload can call the Kubernetes API. Only the platform charts (Prometheus, Alloy, Traefik) get the read-only ClusterRoles they need | chart templates |
| **Network** | `default-deny-all` (ingress + egress) in `llm-app`, then one policy per call-graph edge: ingress→gateway, gateway→catalog/assistant, assistant→catalog/llm, model-verify→llm, monitoring→:8080, DNS→kube-dns. Only `model-download` may leave the cluster (TCP 443, public IPs only, RFC 1918 and 169.254/16 excluded) | `networkpolicies.yaml` |
| **Exposure** | Only the gateway has an Ingress. Everything else is `ClusterIP`. TLS-only entrypoint (HTTP port not published). Traefik `ipAllowList` → 403 for other sources. Host port bound to `127.0.0.1`, so the cluster is not reachable from the LAN | `ingress.yaml`, `modules/kind-cluster` |
| | Chart refuses to render with an empty allowlist (empty would mean allow-all) | `ingress.yaml` |
| **App** | Request body limits (16 KiB), question length validation, upstream timeouts, structured errors without stack traces, API key never logged | `services/` |
| **Secrets** | `llm-api-key`, `gateway-tls`, `grafana-admin`, `incident-webhook` are Kubernetes Secrets generated by Terraform (`random_password`, `tls_*`). Nothing in Git. Consumed only via `secretKeyRef` (never on a command line). The CI script has no `set -x` and never prints values. Terraform outputs are `sensitive` | `app.tf`, `modules/platform` |

### Secrets in the cloud

Terraform would create only the *container* (e.g. an AWS Secrets Manager secret with a KMS key and rotation), not the value. The **External Secrets Operator** runs with IRSA/Pod Identity (AWS) or Workload Identity (GCP) and syncs into a Kubernetes Secret with the same name (`llm-api-key`), so the chart does not change. Alongside that: etcd envelope encryption with KMS, a remote Terraform state backend that is encrypted and access-controlled, and CI that authenticates via OIDC with no static keys.

### Image signing

There is no registry here (images are side-loaded with `kind load`), and cosign signatures are stored as OCI artifacts next to the image in a registry. So signing is **documented, not implemented**. The intended flow:

```bash
# CI (release), after push to the registry:
cosign sign --yes --key awskms:///alias/llmstack-signing  $REGISTRY/llmstack/gateway@sha256:<digest>
cosign attest --yes --key ... --type spdxjson --predicate reports/sbom/gateway.spdx.json $REGISTRY/...@sha256:<digest>
# Cluster: Kyverno ClusterPolicy verifyImages (or Sigstore policy-controller) on namespace llm-app
#   -> rejects any image without a valid signature from that key, and requires the SBOM attestation.
```

Locally the same thing can be shown with `docker run -d -p 5001:5000 registry:2`, `cosign generate-key-pair` (password from an env var, key files git-ignored) and Kind's `containerdConfigPatches` pointing at the local registry.

## Operations

### Rollout and rollback

- Deployments use `maxUnavailable: 0, maxSurge: 1`, `minReadySeconds: 5` and readiness probes. A new pod must be Ready before an old one is removed. A broken release **stalls** while the old pods keep serving.
- Graceful shutdown: native `preStop: sleep 5` lets endpoints drain, then Go `Shutdown()` with a 20 s drain.
- `helm upgrade --atomic` (release path) rolls back automatically on a failed rollout. A failed post-deploy smoke test triggers `helm rollback` from the script.
- Manual rollback: `make rollback ENV=prod [REV=n]`. Helm keeps 10 revisions. `revisionHistoryLimit: 5` on Deployments.
- Infrastructure rollback: revert the commit and re-run `make plan/apply`. State is per environment, so a bad prod apply can't touch dev.

### Availability

- PDB `maxUnavailable: 1` on every Deployment (works at 1 replica in dev and still protects prod during drains).
- `topologySpreadConstraints` by hostname, so prod's 2 replicas land on different workers.
- Gateway HPA (CPU 70%, 1→3 dev, 2→5 prod; fast scale-up, 120 s scale-down stabilisation).

### Scaling the CPU-bound LLM

- **Vertical first.** llama.cpp throughput is bounded by memory bandwidth and cores. Raise `llm.threads` together with the CPU limit (keep them equal; threads > cores hurts), and use `--parallel` slots for concurrent requests.
- **Horizontal next.** Raise `llm.replicas`. Each replica is stateless apart from the read-only model. With a node-local RWO volume, replicas must share the node. On a real cluster use RWX storage (EFS/Filestore) or a per-pod init download from an internal mirror.
- **Autoscale on the right signal.** CPU is always near 100% while generating, so CPU-HPA is a poor signal. Use KEDA or a custom-metrics HPA on queue depth (`llamacpp:requests_deferred` / `requests_processing`) or on assistant p95 latency. Scale-up is slow (model load ~5-10 s, plus node provisioning), so keep `minReplicas ≥ 2` in prod.
- **Dedicated node pool** (compute-optimised, AVX-512/AMX on x86 or Graviton) with a taint and toleration, so the LLM does not starve the web tier, plus the cluster autoscaler for that pool.
- **Protect the backend.** Cap `max_tokens`, apply rate limits at the gateway, and use timeouts (assistant 110 s, gateway 120 s) so slow generations fail predictably.

### Observability

| Signal | How | Where to look |
|---|---|---|
| Logs | JSON logs from every pod → Alloy (`loki.source.kubernetes`) → Loki, labels `namespace/pod/container/app/level` | Grafana → Explore → Loki, or the dashboard's logs panel |
| Uptime probe | Prometheus scrapes `up{service="gateway"}`; kubelet probes; `GatewayDown` alert | Dashboard "Gateway uptime" |
| Latency | `http_request_duration_seconds` histogram per service/route | Dashboard "p95 latency by route" |
| Error rate | `http_requests_total{code}` | Dashboard "Gateway 5xx ratio"; `GatewayHighErrorRate` |
| Scheduled job | kube-state-metrics `kube_job_status_*`, `kube_cronjob_status_last_successful_time` | Dashboard panels; `ModelVerifyJobFailed`, `ModelVerifyNotSucceededRecently` |
| Autoscaling | `kube_horizontalpodautoscaler_status_*` | Dashboard "Gateway replicas vs HPA desired" |

**Alert rules** (`PrometheusRule llmstack-alerts`): `GatewayHighErrorRate` (critical, >5% 5xx for 2m), `GatewayDown`, `LLMUnavailable`, `GatewayHighLatencyP95` (warning), `ModelVerifyJobFailed`, `ModelVerifyNotSucceededRecently`.

**Incident channel wiring.** Alertmanager's default route goes to the `incident-channel` receiver. Its webhook URL is read from the `incident-webhook` Secret via `url_file`, so the URL never appears in Helm values or logs. To connect Slack: `export TF_VAR_incident_webhook_url=https://hooks.slack.com/services/...` then `make apply`. With Slack this would use `slack_configs` (with `api_url_file`); for paging, `pagerduty_configs` with a routing key. Each critical alert carries a `runbook_url` pointing at the matching section of [RUNBOOK.md](RUNBOOK.md#7-alert-runbooks).

**Incident handling.** Alert → on-call acknowledges in the channel → follows the runbook section → mitigates (rollback first if a release went out recently) → writes a short post-incident note covering timeline, root cause and follow-up actions.
